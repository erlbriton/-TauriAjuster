TauriAjuster — техническое описание проекта
Назначение и область
Приложение для работы с промышленными контроллерами (регуляторами). Основная функция — многоканальный осциллограф содержимого Modbus-регистров в реальном времени. Дополнительные подсистемы: работа с INI-файлами устройств, ведение базы устройств на диске, обновление прошивки, отчёты. Стек: Tauri v2, Rust (backend), TypeScript (frontend), PixiJS (рендеринг). Объём ~25 000 строк.

Осциллограф как ядро проекта
Осциллограф — критическая часть, ради которой выбирались все остальные технологии. Задача: считывать значения Modbus-регистров контроллера с максимально возможной частотой и отображать их в реальном времени по нескольким каналам. Классически такая задача решается на C++/Qt, поскольку TypeScript-рендеринг через DOM или Canvas 2D не выдерживает нужной частоты обновления.

Решение — вынести отрисовку на GPU через PixiJS (WebGL/WebGPU). Рендеринг волновых форм, сетки, курсоров и каналов выполняется на видеокарте; CPU занят подготовкой данных и транспортом. React не используется — весь UI нативный, DOM не участвует в горячем пути. Это даёт частоту, недостижимую для чисто CPU-подходов.

Две версии одной логики
Осциллограф работает в двух средах: нативное приложение (Tauri, webview) и браузер. Логика рендеринга и обработки данных общая; различия локализованы в слое транспорта (src/oscilloscope/comm/): в Tauri — команды Rust и события serial-data, в браузере — Web Serial API. В браузерной версии достичь максимальной частоты оказалось проще из-за отсутствия прослойки между JS и GPU, которую вносит Tauri webview. Это означает, что архитектурно осциллограф не зависит от Tauri и может использоваться как самостоятельное веб-приложение.

Структура кода осциллографа
Модуль src/oscilloscope/ разделён на слои:

graphics/ — PixiJS-рендерер (PixiView, Renderer, WaveformRenderer).

scope/ — логика жизненного цикла, каналов, композиции, привязок, команд (OscilloscopeLoop, OscilloscopeChannels, OscilloscopeComposite, OscilloscopeRenderer и др.).

comm/ — транспорт (Modbus, Serial).

core/ — буферизация и запись (Archive, Channel, Recorder, RecFileReader, RecFileWriter).

ui/ — панели, модалки, тулбар, курсоры (BottomPanels, ChannelPropertiesModal, CursorsFooter, TimelineScrollbar, Toolbar и др.).

config/ — настройки.

Такое разделение изолирует горячий путь (графика + цикл опроса) от UI, что позволяет менять интерфейс, не затрагивая производительность.

Подсистема INI-файлов
INI-файлы — вспомогательная обвязка. Каждый файл начинается строго с 5 строк:

text
[DEVICE]
ID=...
Location=...
Version=...
Date=...
Далее секции [RAM], [XRAM], [CD], [FLASH], [VARS] с параметрами Modbus. Кодировка — Windows-1251, декодируется на стороне TypeScript.

Rust-команда scan_devices_folder читает только первые 5 строк каждого файла через BufReader с буфером 1 КБ (вместо стандартных 8 КБ) — это обеспечивает мгновенный старт на базе в сотни файлов. TypeScript-функция registerDeviceFromHeader регистрирует устройство «лёгким» путём: isHeaderOnly = true, без парсинга секций параметров и без отрисовки таблицы. Полное содержимое читается однократно при первом клике по устройству в дереве (команда read_ini_file), после чего флаг сбрасывается.

Синхронизация с диском
Кнопка «Обновить список устройств» вызывает resyncDevicesFromDisk. Функция использует last_modified_ms (mtime из Rust) как дешёвый сигнал изменения: полное чтение выполняется только для файлов, чей mtime отличается от сохранённого. Обрабатываются добавления, удаления и смена location/id («переезды»). На неизменной базе из 717 файлов синхронизация занимает секунды вместо минут. Регистрация новых файлов идёт через registerDeviceFromHeader (лёгкий путь), изменённых — через полное чтение и updateDeviceInRegistry.

Структура базы на диске
Рядом с исполняемым файлом:

text
<exe>/
  Devices/         — INI-файлы, разложенные по подпапкам (Location / версия)
  BackUp/          — старые INI, плоская папка (только имена файлов)
  TemplateDevice/  — шаблоны для создания новых устройств
  XLT/             — сгенерированные отчёты (.xlsx, .csv)
Путь к базе берётся из AppConfigState.base_dir, а не из папки exe напрямую — это позволяет менять базу во время работы.

Глобальное состояние
Объект AppState создаётся в main.ts и публикуется в window.appState через приведение типа через unknown (из-за конфликта объявлений в src/ui/tree.ts, где window.appState типизирован как TableEditorState). Это даёт доступ к состоянию модулям, не получающим его через параметры, в частности tree-render.ts при полной загрузке файла по клику.

Ключевые ограничения и риски
Производительность осциллографа критична. Любая замена PixiJS на CPU-рендеринг (Canvas 2D, SVG, DOM), любое вмешательство в scope/ или graphics/ требует замера частоты до и после.

Единый код для Tauri и браузера. Различия допустимы только в слое транспорта.

TS 5.7+ требует явного типа Uint8Array<ArrayBuffer> для BlobPart в конструкторе File — иначе ошибка SharedArrayBuffer.

entry.lastModified в fileStore должен совпадать с last_modified_ms из Rust, иначе файл будет считаться изменённым при каждом resync.
